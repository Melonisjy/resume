## 배경

배포 후 페이지 초기 로딩이 체감상 느리다는 피드백이 있었다.  
딱 눈에 띄는 병목이 없었고, 코드를 눈으로 보는 것만으로는 어디가 문제인지 파악이 안 됐다.

그래서 번들을 직접 들여다보기로 했다.

---

## @next/bundle-analyzer 설치

```bash
npm install @next/bundle-analyzer
```

`next.config.js`에 아래처럼 감싸주면 된다.

```js
const withBundleAnalyzer = require('@next/bundle-analyzer')({
  enabled: process.env.ANALYZE === 'true',
});

module.exports = withBundleAnalyzer({
  // 기존 설정
});
```

분석할 때는 환경변수를 넘겨서 빌드하면 된다.

```bash
ANALYZE=true npm run build
```

빌드가 끝나면 브라우저에서 트리맵이 열린다.  
각 모듈이 번들에서 얼마나 차지하는지 블록 크기로 시각화해준다.

---

## 뭐가 문제였나

트리맵을 펼쳐보니 눈에 띄는 덩어리가 두 개 있었다.

1. **FullCalendar 관련 패키지** — 캘린더 컴포넌트가 페이지 로드 시점부터 번들에 포함되고 있었다.
2. **jszip** — 6개 파일에서 최상단에 정적으로 import하고 있었는데, 실제로는 특정 버튼을 눌렀을 때만 필요한 코드였다.

둘 다 "초기 로드에 필요하지 않은데 처음부터 다 불러오고 있는" 케이스였다.

---

## FullCalendar — dynamic import 적용

FullCalendar는 SSR이 필요 없는 컴포넌트다.  
서버에서 렌더할 필요도 없고, 초기 페이지 로드 타이밍에도 포함될 필요가 없었다.

기존 코드는 이런 식이었다.

```tsx
import FullCalendar from '@fullcalendar/react';
import dayGridPlugin from '@fullcalendar/daygrid';
```

이걸 `next/dynamic`으로 바꿨다.

```tsx
import dynamic from 'next/dynamic';

const FullCalendar = dynamic(() => import('@fullcalendar/react'), {
  ssr: false,
});
```

`ssr: false`를 붙이면 두 가지가 동시에 된다.

- 서버에서 렌더링을 건너뛴다 (FullCalendar는 `window`에 의존하는 로직이 있어서 SSR하면 오류가 날 수 있다)
- 해당 컴포넌트가 실제로 필요할 때 클라이언트에서 따로 로드된다 (코드 스플리팅)

캘린더가 없는 페이지에서는 FullCalendar 번들을 아예 로드하지 않게 된다.

---

## jszip — 함수 내 동적 import로 변경

jszip은 파일을 압축하거나 압축 해제할 때 쓰는 라이브러리다.  
기존에는 파일 최상단에 정적으로 import하고 있었다.

```ts
import JSZip from 'jszip';
```

이렇게 하면 해당 모듈을 포함한 페이지가 초기 로드될 때 jszip 전체가 번들에 포함된다.  
실제로 jszip을 쓰는 건 다운로드 버튼을 눌렀을 때뿐인데, 처음부터 불러올 이유가 없었다.

6개 파일 모두 동일한 패턴으로 수정했다.

```ts
// before
import JSZip from 'jszip';

async function downloadFiles() {
  const zip = new JSZip();
  // ...
}
```

```ts
// after
async function downloadFiles() {
  const { default: JSZip } = await import('jszip');
  const zip = new JSZip();
  // ...
}
```

함수 안에서 `await import()`를 쓰면, 해당 함수가 실제로 실행될 때 jszip을 로드한다.  
초기 번들에서 빠지고, 필요한 시점에만 네트워크 요청이 한 번 나간다.

`default:` 구조 분해를 쓰는 이유는 jszip이 CommonJS 모듈이라서, default export를 명시적으로 꺼내야 하기 때문이다.

---

## 결과

세 가지 변경만으로 초기 번들 사이즈가 눈에 띄게 줄었다.  
FullCalendar와 jszip 모두 필요한 시점에 따로 로드되기 때문에, 실제 사용하는 기능에서의 반응 속도는 그대로고 초기 진입이 가벼워졌다.

---

## 정리

이번 작업에서 기준으로 삼은 게 하나 있다.

> "이 모듈이 페이지 첫 진입 시점에 반드시 필요한가?"

아니라면 dynamic import 후보다.  
특히 무거운 UI 라이브러리(차트, 캘린더, 에디터)와 특정 액션에만 쓰이는 유틸(압축, 파싱, 변환)은 대부분 초기 로드에 포함시킬 필요가 없다.

bundle-analyzer는 이런 판단을 눈으로 할 수 있게 해주는 도구다.  
번들 최적화를 고민하기 전에 먼저 들여다보는 게 순서가 맞는 것 같다.
